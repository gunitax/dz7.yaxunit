# AGENTS.md

Руководство для ИИ-агентов и разработчиков, работающих с этим репозиторием.

Git-репозиторий: remote — `github.com/gunitax/dz7.yaxunit` (публичный), ветка `main`. В `.gitattributes` стоит `* -text` — конвертация переводов строк выключена; артефакты сборки и отчёты (`build/`) в `.gitignore`.

## Что это за проект

XML-выгрузка демонстрационной конфигурации «Библиотека стандартных подсистем» (БСП):
- Конфигурация: `БиблиотекаСтандартныхПодсистемДемо`, поставщик — Фирма «1С», версия **3.2.1.569**.
- Формат: выгрузка Конфигуратора («Сохранить конфигурацию в файлы»), версия формата **2.21** (платформа 8.5.1). Это НЕ проект 1C:EDT — структура папок иная.
- Режим совместимости **8.5.1**, управляемое приложение, режим обычного приложения не используется.
- Вариант встроенного языка: **русский**. Все имена метаданных, переменных и код — на русском.
- Лицензия кода: CC BY 4.0 (заголовок в начале каждого `.bsl` основной конфигурации).

Масштаб: 12 629 файлов, ~277 МБ; 3051 файл `.bsl` (~1,33 млн строк), 8057 XML. Состав: 804 общих модуля, 116 справочников, 259 регистров сведений, 154 обработки, 166 ролей, 60 регламентных заданий, 52 отчёта, 25 документов, 121 общая форма, 135 перечислений, 251 константа, 96 общих команд, 69 пакетов XDTO, 13 веб-сервисов, 4 HTTP-сервиса, 18 подсистем верхнего уровня (236 с вложенными).


## Структура репозитория

Выгрузка конфигурации лежит в каталоге `1c/` — метаданные разложены по разделам:

- `1c/Configuration.xml` — корневой объект конфигурации (свойства, роли по умолчанию, интерфейсы).
- `1c/ConfigDumpInfo.xml` — служебный файл соответствия версий объектов выгрузки. Генерируется Конфигуратором.
- `1c/extensions/` — выгрузки расширений конфигурации, по одной папке на расширение (см. раздел «Доработки и расширения»). Основная конфигурация её не использует.
- `vendor/yaxunit/25.12/YAxUnit-25.12.cfe` — официальный релиз движка YAxUnit (чужой код: не редактировать, не выгружать из базы, не переносить в `1c/`; версия и SHA-256 — в `vendor/yaxunit/25.12/README.md`).
- `tests/` — JSON-конфиги запуска YAxUnit (`unit.json`, `integration.json`, `single.json`, `all.json` — общий прогон); отчёты и коды результата пишутся в `build/tests/` (каталог в `.gitignore`).
- `1c/extensions/СчетаМагазинаТесты/` — расширение тестов проекта (см. раздел «Тестирование YAxUnit»).
- `1c/Ext/` — модули приложения: `SessionModule.bsl` (модуль сеанса), `ManagedApplicationModule.bsl` (управляемое приложение), `ExternalConnectionModule.bsl`, `OrdinaryApplicationModule.bsl`, интерфейсы, заставка.
- Разделы метаданных (папки во множественном числе): `Catalogs` (справочники), `Documents` (документы), `InformationRegisters` (регистры сведений), `AccumulationRegisters` (регистры накопления), `AccountingRegisters` (регистры бухгалтерии), `CommonModules` (общие модули), `CommonForms`, `CommonCommands`, `Enums`, `Subsystems`, `Roles`, `Reports`, `DataProcessors` (обработки), `ScheduledJobs`, `ExchangePlans`, `WebServices`, `HTTPServices`, `XDTOPackages` и т.д.

Внутри каждого раздела на один объект метаданных приходится пара «файл + папка»:

```
1c/Documents/
  _ДемоЗаказПокупателя.xml        <- описание метаданных объекта (реквизиты, табличные части, движения)
  _ДемоЗаказПокупателя/
    Ext/
      ObjectModule.bsl            <- модуль объекта
      ManagerModule.bsl           <- модуль менеджера
      Help.xml, Help/ru.html
    Forms/
      ФормаДокумента.xml          <- описание формы
      ФормаДокумента/Ext/Form.xml <- макет формы (элементы)
      ФормаДокумента/Ext/Form/Module.bsl <- модуль формы
    Templates/                    <- макеты
```

Имена файлов модулей: `Module.bsl` (общий модуль), `ObjectModule.bsl`, `ManagerModule.bsl`, `Form/Module.bsl` (форма), `Template.xml` (макет), `Command/Module.bsl` (команда).

Объекты демонстрационной конфигурации имеют префикс `_Демо` (например, `_ДемоЗаказПокупателя`). Подсистемы: `СтандартныеПодсистемы`, `Администрирование`, `ТехнологияСервиса` и `_Демо*` для демонстрационных разделов.

## Критические правила работы с файлами

1. **Кодировка и переводы строк.** Все текстовые файлы — UTF-8 **с BOM**, переводы строк **CRLF**. При правках сохраняйте и то, и другое: без BOM Конфигуратор не загрузит файл, смешение переводов строк ломает diff и повторную выгрузку. Единственное штатное исключение — тексты запросов внутри `<QueryText>` в XML и файлы справки `Help/ru.html`: там платформа пишет одиночный LF, это нормально и править не нужно.
2. **UUID не трогать.** `uuid` в XML идентифицирует объект метаданных в информационной базе. Смена UUID = потеря данных при обновлении.
3. **`ConfigDumpInfo.xml` не редактировать руками.** Он управляется Конфигуратором при сохранении/загрузке выгрузки. После правок через Конфигуратор он обновится сам; ручные правки почти всегда приводят к полному перезаливанию конфигурации.
4. **Структуру XML не реорганизовывать.** Порядок элементов и отступы (табуляция) значимы для повторной загрузки и читаемости diff. Правки — точечные, в существующих узлах.
5. **Бинарные файлы не редактировать**: `ParentConfigurations.bin`, `StandaloneConfigurationContent.bin`, картинки в `CommonPictures/`, `_ДемоРасширение.cfe`.
6. Изменение состава объектов (добавление/удаление файла объекта) без обновления `Configuration.xml` и `ConfigDumpInfo.xml` сломает загрузку — состав объектов меняется только через Конфигуратор.

## Соглашения по коду (стиль БСП)

Суффиксы общих модулей задают контекст вызова — при создании новых модулей следуйте той же схеме:

| Суффикс | Контекст |
|---|---|
| — (без суффикса) | сервер, серверные вызовы |
| `Клиент` | только клиент (клиент-серверный модуль) |
| `КлиентСервер` | клиент + сервер без контекстных вызовов |
| `ВызовСервера` | клиентский модуль для обращения к серверу |
| `ПовтИсп` | повторное использование возвращаемых значений |
| `Переопределяемый` | модуль, переопределяемый в конфигурации-потребителе |
| `Служебный` | внутренние процедуры БСП, не для прикладного использования |
| `Глобальный` | точка входа (в свойствах модуля) |

Прочие соглашения:
- Заголовок лицензии CC BY 4.0 в начале каждого модуля — сохранять.
- Области кода: `#Область ПрограммныйИнтерфейс` (экспортные), `#Область СлужебныеПроцедурыИФункции`, `#Область ОбработчикиСобытий` — соблюдать порядок.
- Экспортные процедуры/функции помечаются `Экспорт` и снабжаются doc-комментарием с разделом `Параметры:` (типы через `-` на отдельных строках).
- Запросы — на языке запросов 1С, конкатенация строк запроса через `<<КодЗапроса>>` в типовых процедурах БСП не используется; текст запроса — строковый литерал.
- Имена: `КэмелКейс` на русском, без подчёркиваний (кроме префикса `_Демо`); в текстах и сообщениях вместо «ё» — «е».

Известный долг: модули расширения `СчетаМагазина` исторически без лицензионного заголовка; в `СчетаМагазинаHTTP` области и doc-комментарии добавлены, в `СчетаМагазинаДанные` и `СчетаМагазинаМетаданные` области и заголовок ещё не заведены, запросы собираются конкатенацией. При следующей правке модулей долг закрывать, новый код писать по соглашениям.

## Доработки и расширения

**Все доработки конфигурации выполняются в расширениях (если явно не указано иное).** Основная конфигурация — поставляемая БСП, её не изменять.

- Расширения хранятся в `1c/extensions/<ИмяРасширения>/` — каждая папка является самостоятельной выгрузкой расширения (свой `Configuration.xml` и `ConfigDumpInfo.xml`).
- Эталон минимального состава — `1c/extensions/_ДемоПустоеРасширение/` (корень + `Languages/Русский.xml`). От `_ДемоРасширение` в этой поставке остался только бинарник `_ДемоРасширение.cfe`, файловой выгрузки нет: как эталон формата он не годится. Живой пример — `1c/extensions/СчетаМагазина/` (собственные объекты, HTTP-сервис, без заимствований).
- Новые объекты — собственные для расширения (без `ObjectBelonging` в `Properties`); заимствованные — с `ObjectBelonging = Adopted` первым свойством и UUID основной конфигурации.
- Назначение расширения — «Дополнение» (`AddOn`) для новых объектов, «Адаптация» (`Customization`) для правки форм/модулей основной конфигурации.
- Режим совместимости расширения (`ConfigurationExtensionCompatibilityMode`) должен быть **не выше** режима совместимости основной конфигурации (`CompatibilityMode`, здесь 8.5.1). Режим выше — расширение не подключается («Режим совместимости расширения больше режима совместимости основной конфигурации»).
- Канонический обязательный состав расширения: заимствованный язык (`Languages/Русский.xml`, `ObjectBelonging = Adopted`, запись `<Language>Русский</Language>` в `ChildObjects` корня) и `xr:PropertyState` (CommandInterface, MainSectionCommandInterface = Extended) в `InternalInfo` корня. Оговорка: на 8.5.1 расширение без языка загружается и работает (так устроен `СчетаМагазина`), но `cfe-validate` выдаёт предупреждение «No Language entries in ChildObjects», а первая же перевыгрузка Конфигуратором перепишет файлы — канон лучше держать. `DefaultRoles` в расширениях этой поставки не используется.

## Сборка и проверка

Это выгрузка, а не собираемый проект — «сборки» в привычном смысле нет. Жизненный цикл изменений:

- **Загрузка в Конфигуратор**: Конфигуратор → «Загрузить конфигурацию из файлов» → каталог `1c/`. Обратная операция — «Сохранить конфигурацию в файлы» (обновляет `ConfigDumpInfo.xml`).
- **Расширения**: Конфигуратор → Конфигурация → «Расширения конфигурации» → «Добавить» → «Загрузить из файлов» → папка расширения в `1c/extensions/`. Обратно — «Выгрузить в файлы» в ту же папку.
- **Тестовая база — копия**, работа с ней идёт **напрямую с файловой базой** (см. раздел «Файловая тестовая база»): `D:\infobase\dz7.yaxunit`, пользователь `Администратор`, пароль пустой. Копия одноразовая: загружать расширения, обновлять конфигурацию БД и проверять синтаксис можно свободно, отдельного разрешения это не требует.
- **Проверка расширения в базе**: `db-cfe-admin check -InfoBasePath "D:\infobase\dz7.yaxunit" -UserName "Администратор" -Name <Имя> -Checks apply,modules -Context ThinClient,Server` — применимость (`/CheckCanApplyConfigurationExtensions`) и синтаксис модулей (`/CheckConfig -ThinClient -Server -Extension`). Обе команды только читают базу.
- **Статическая проверка до загрузки**: `cfe-validate` по папке расширения с `-ConfigPath 1c` — структура XML, состав, заимствования, права.
- **Загрузка из файлов пакетно**: `1cv8.exe DESIGNER /F "D:\infobase\dz7.yaxunit" /N "Администратор" /LoadConfigFromFiles <папка> -Extension <Имя>` (сама создаёт расширение), затем `/UpdateDBCfg -Extension <Имя>`. Команды `DESIGNER` выполняются по одной за запуск. При пустом пароле аргумент `/P` не передавать: PowerShell выбрасывает пустой аргумент, и платформа отвечает «Пользователь ИБ не идентифицирован» (скрипты `skills/db-*` это уже учитывают).
- **Запуск**: демо-конфигурация в режиме управляемого приложения платформы 8.5.1.

Текстовые правки (код, строки интерфейса) допустимы прямо в файлах выгрузки; структурные изменения состава метаданных делаются в Конфигураторе с последующим сохранением выгрузки обратно в репозиторий.

## Рабочее расширение `СчетаМагазина`

Назначение `AddOn`, собственные объекты, HTTP-сервис `СчетаМагазина` с корневым URL `objects` (фактический путь публикации — `/hs/objects/...`):

| Метод | Шаблон | Обработчик | Смысл |
|---|---|---|---|
| GET | `/types` | `НайтиТипы` | реестр поддерживаемых типов (справочники и документы) |
| GET | `/type` | `ОписатьТип` | JSON-схема типа: поля, табличные части, типы, обязательность |
| GET | `/search` | `НайтиОбъекты` | поиск по наименованию/номеру, до 100 записей |
| GET | `/object` | `ПрочитатьОбъект` | чтение объекта по UUID |
| POST | `/object` | `СоздатьОбъект` | создание; только `_Демо*` и `Валюты`, документ создаётся непроведённым |
| POST | `/prices/reprice` | `ПереоценитьТовары` | переоценка цен на процент с даты; ошибки входа — `400 invalid_data` |

Логика: `CommonModules/СчетаМагазинаМетаданные` (реестр, схема, правила записи), `CommonModules/СчетаМагазинаДанные` (разбор тела, приведение типов, поиск, чтение, проверка сумм, запись в транзакции с `ПроверитьЗаполнение`) и `CommonModules/СчетаМагазинаHTTP` (обработчики HTTP-сервиса; модуль сервиса — делегаты). Права проверяются через `ПравоДоступа`.

Проверка сумм строк: `Количество > 0`, `Цена > 0`, `Сумма = Окр(Количество × Цена, 2)`. При нарушении сервис отвечает 422 `invalid_amounts` с `details` вида `{path, message}` и не пишет объект. Проверяются документы, у которых в табличной части есть записываемые числовые `Количество`, `Цена` и `Сумма`.

Переоценка цен: `POST /prices/reprice` (`{"items": [...], "percent": 7, "date": "ГГГГ-ММ-ДД"}`). Расчёт — `СчетаМагазинаДанные.РассчитатьНовуюЦену` (без базы, половина рубля — вверх), чтение и запись — `СчетаМагазинаДанные.ПереоценитьТовары`, валидация и JSON-ответ — `СчетаМагазинаHTTP.ПереоценитьТовары`. Старая цена — `СрезПоследних` на `КонецДня(Дата - 86400)`, новая — запись на `НачалоДня(Дата)`; товар без записи на конец предыдущего дня возвращается в `skipped` с `no_price`; повторный запрос с той же датой идемпотентен; ошибки входа — `400 invalid_data` с `details`.

Публикация в тестовой среде: `http://localhost/dz7/`, HTTP-сервис — `http://localhost/dz7/hs/objects/...`, Basic Auth (пользователь `Администратор`, пароль пустой). `default.vrd` — в `D:\infobase\dz7.pub`, Apache Alias `/dz7`, `publishExtensionsByDefault="true"`. Примеры запросов — `requests/СчетаМагазина.http`. Тесты — в `1c/extensions/СчетаМагазинаТесты/`

## Запрещённые действия

При работе с информационной базой и Конфигуратором:

- **Никогда не завершать сеансы пользователей.** Даже если операция требует монопольного режима (обновление конфигурации базы данных, загрузка конфигурации из файлов) — не завершайте активные сеансы и не принуждайте базу к монопольному режиму. Если операция блокируется работающими пользователями — сообщите об этом и дождитесь явного решения пользователя.
- **Не применять расширения к рабочим базам автоматически.** Применение расширения к информационной базе (загрузка расширения, «Обновить конфигурацию базы данных», установка безопасного режима и защиты от опасных действий) выполняется только по явной команде пользователя. Без команды — только подготовка и правка файлов расширения в `1c/extensions/`. Исключение — тестовая файловая копия `D:\infobase\dz7.yaxunit` (Администратор, пароль пустой): загрузка туда расширений для проверки разрешена штатно (см. «Сборка и проверка»).

## Навыки и MCP

**Правило проекта: новые навыки добавляются только в этот репозиторий — `<корень>/.dsh/skills/<имя>/SKILL.md`.** Профильные `~/.dsh/skills` общие для всех проектов (V6, V7, …) и не расширяются: новый навык, положенный туда, «протечёт» в чужие сессии. Проектный слой имеет приоритет над профильным, поэтому локальная копия может переопределить общий навык — но отключённая локальная копия профильную не перекрывает (флаг `disable-model-invocation` надо ставить в самом файле).

- Навыки 1С (`bsl-*`, `cfe-*`, `db-*`, `make-*`) пока живут в профиле `~/.dsh/skills`; раскладку проекта они берут из этого файла.
- Навыки `speckit-*` в профиле отключены (`disable-model-invocation: true`) — в этом проекте спецификации не ведутся. В V6 они возвращены проектными копиями в `D:\AI.V6\.dsh\skills`.
- Плагин Superpowers (`dsh-superpowers`) подключён в профиль и даёт 14 процессных навыков; его bootstrap-секция отключается через `- id: superpowers` → `config.bootstrap: false` в `cordis.patch.yml` профиля.
- **MCP-серверы проектного слоя не имеют**: DSH получает их из настроек сессии/профиля (`session/new` валидирует stdio/HTTP-серверы), отдельного `<корень>/.dsh/mcp` нет. Без явной команды MCP не подключать; при подключении фиксировать здесь сервер, транспорт и назначение.

## Работа с веб-поиском

Если при выполнении задачи использовался веб-поиск или чтение веб-страниц (1С:ИТС, ИТС.1С, документация платформы, форумы и т.п.), в конце ответа всегда приводите раздел «Sources:» со списком markdown-ссылок на все ресурсы, которые использовались при подготовке ответа. Это требование пользователя: он должен иметь возможность проверить первоисточники.
