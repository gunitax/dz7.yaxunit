# Спецификация: переоценка товаров через сервис объектов

**Дата:** 2026-11-11  
**Статус:** на согласовании  
**Основание:** ТЗ «Переоценка товаров через сервис объектов»  
**Расширения:** `СчетаМагазина` (сервис объектов), `СчетаМагазинаТесты` (YAxUnit)

## 1. Цель

Сервис объектов принимает одним запросом переоценку выбранных товаров на процент
с даты. Повторный запрос с той же датой не меняет результат. Каждое правило
подтверждено тестом YAxUnit, написанным до кода.

## 2. Границы

В рамках задачи:

- новый маршрут `POST /hs/objects/prices/reprice` в существующем HTTP-сервисе
  `СчетаМагазина` (`RootURL = objects`);
- экспортная функция расчёта новой цены без обращения к базе;
- экспортная функция переоценки: чтение старых цен, запись новых, пропуск товаров
  без цены, идемпотентность по дате;
- валидация входа и ответы `200` / `400` / `415` / `500`;
- юнит- и интеграционные тесты в расширении `СчетаМагазинаТесты`, общий конфиг
  запуска, примеры запросов `.http`.

Вне рамок (из ТЗ):

- несколько цен одного товара внутри одного дня;
- цены, записанные позже даты переоценки (они остаются и действуют со своих дат);
- товары дешевле 1 рубля;
- виды цен, валюты, НДС, отмена переоценки;
- публикация и проверка маршрута в браузере (достаточно примера `.http`);
- изменение основной конфигурации.

## 3. Принятые решения

### 3.1. Код ошибки входа

Для нового маршрута используется `invalid_data` (выбрано по ТЗ). Существующий
`СоздатьОбъект` продолжает возвращать `invalid_request` — его поведение не меняется.
Форма ответа единая:

```json
{
  "error": {
    "code": "invalid_data",
    "message": "Ошибка входных данных",
    "details": [
      { "path": "percent", "message": "Процент 150 недопустим: допустимо от -50 до 100, кроме 0" }
    ]
  }
}
```

`path` — `null` для ошибки уровня тела, `items`, `items[i]`, `percent`, `date`.
`details` содержит все найденные ошибки, а не первую.

### 3.2. Ноль — это цена

Цена `0` в регистре — допустимая старая цена. `no_price` возвращается только
тогда, когда на конец предыдущего дня записи о цене товара нет вообще.
Переоценка нулевой цены даёт `0` и не является пропуском.

### 3.3. Идентификаторы в ответе

`id` в `repriced` и `skipped` — тот же канонический строковый UUID, который
пришёл в `items` (сервис отдаёт UUID в нижнем регистре). Порядок внутри каждого
массива повторяет порядок `items`.

### 3.4. Размещение логики

- `СчетаМагазинаHTTP.ПереоценитьТовары(Запрос)` — разбор тела, валидация,
  формирование `HTTPСервисОтвет`; вызывает функцию данных.
- `СчетаМагазинаДанные.РассчитатьНовуюЦену(СтараяЦена, Процент)` — чистая
  функция расчёта, без обращений к базе.
- `СчетаМагазинаДанные.ПереоценитьТовары(Товары, Процент, ДатаПереоценки)` —
  чтение старых цен, запись новых в транзакции, результат `repriced`/`skipped`.
- Модуль HTTP-сервиса `HTTPServices/СчетаМагазина/Ext/Module.bsl` — только
  делегат: `Возврат СчетаМагазинаHTTP.ПереоценитьТовары(Запрос);`.

Новый общий модуль не создаётся: это позволило бы не менять состав метаданных
и использовать существующие JSON-хелперы `СчетаМагазинаHTTP`.

### 3.5. Границы периода

- Старая цена: `СрезПоследних` на `ДобавитьКДате(НачалоДня(ДатаПереоценки), "Секунда", -1)`,
  то есть `23:59:59` предыдущего дня.
- Новая цена: запись с периодом `НачалоДня(ДатаПереоценки)`, то есть `00:00:00`.
- Запись на тот же период и товар заменяет прежнюю (независимый периодический
  регистр, ключ «период + Номенклатура»).

### 3.6. Процент в сообщении об ошибке

Для недопустимого числа процент берётся из тела запроса как JSON-токен
(цифры, минус, точка, экспонента), а не форматируется локалью. Это даёт
`150`, `150.5`, `-50.0` в том виде, в каком они пришли. Допустимый диапазон
в тексте: `от -50 до 100, кроме 0`.

### 3.7. Тестовые данные

Тесты создают товары сами, через `Справочники._ДемоНоменклатура.СоздатьЭлемент()`
(обязательный `ВидНоменклатуры` берётся из демо-базы). Конструктор YAxUnit для
товаров не используется: тестам нужна собственная очистка, в том числе после
красного прогона.

Очистка — явная, в `Попытка / Исключение / ВызватьИсключение` вокруг тела теста:
сначала удаляются все записи регистра по товару, затем сам товар. Это убирает
и записи, созданные тестом, и автоматическую цену, которую демо-конфигурация
пишет при записи товара, и записи проверяемого кода. После зелёного прогона
очистка вызывается ещё раз в конце теста.

## 4. API

### 4.1. Запрос

`POST /hs/objects/prices/reprice`

```json
{
  "items": ["<id товара>", "<id товара>"],
  "percent": 7,
  "date": "2026-12-01"
}
```

- `items` — непустой массив строковых UUID `Справочник._ДемоНоменклатура`;
  без повторов; каждый товар существует и не помечен на удаление.
- `percent` — число (`Число`), дробное допустимо; от `-50` до `100` включительно,
  кроме `0`.
- `date` — строка строго `ГГГГ-ММ-ДД`.
- `Content-Type: application/json`.

### 4.2. Успешный ответ `200`

```json
{
  "repriced": [
    { "id": "<id>", "oldPrice": 150, "newPrice": 161 }
  ],
  "skipped": [
    { "id": "<id>", "reason": "no_price" }
  ]
}
```

`repriced` — товары, у которых была цена; `skipped` — только `no_price`.
Массивы могут быть пустыми; порядок — как в `items`.

### 4.3. Ошибки

- `400 invalid_data` — тело не JSON-объект, ошибки полей; `details` с путями.
- `415 unsupported_media_type` — `Content-Type` не `application/json`
  (поведение как у `СоздатьОбъект`).
- `500 internal_error` — непредвиденная ошибка записи/чтения; тело в форме
  существующего сервиса, в журнал регистрации.

Валидация выполняется до чтения и записи цен. Если есть ошибки полей, функция
данных не вызывается; в регистре ничего не меняется.

Сообщения валидации:

| Поле | Условие | Сообщение (содержит) |
| --- | --- | --- |
| `items` | не массив / пустой | `items должен быть непустым массивом идентификаторов` |
| `items[i]` | не строка / не UUID | `Некорректный идентификатор товара` |
| `items[i]` | повтор | `Товар указан повторно` |
| `items[i]` | нет или помечен на удаление | `Товар не найден или помечен на удаление` |
| `percent` | не число | `Процент должен быть числом от -50 до 100, кроме 0` |
| `percent` | `0`, `< -50`, `> 100` | `Процент <токен> недопустим: допустимо от -50 до 100, кроме 0` |
| `date` | не строка / не `ГГГГ-ММ-ДД` | `Дата должна быть строкой ГГГГ-ММ-ДД` |

### 4.4. Примеры `.http`

В `requests/СчетаМагазина.http` добавляются:

- успешная переоценка трёх товаров на `+7` с даты;
- отказ по проценту `150` с ожидаемым `400 invalid_data`.

## 5. Расчёт

```
НоваяЦена = Окр(СтараяЦена * (1 + Процент / 100), 0, РежимОкругления.Окр15как20)
```

- округление до целых рублей;
- половина рубля — вверх (`Окр15как20`);
- функция не обращается к базе и не валидирует вход.

Примеры:

| Старая | Процент | До округления | Новая |
| ---: | ---: | ---: | ---: |
| 100 | +7 | 107.0 | 107 |
| 151 | −30 | 105.7 | 106 |
| 150 | +7 | 160.5 | 161 |

## 6. Данные и запись

Регистр: `РегистрСведений._ДемоЦеныНоменклатуры`, независимый, периодический
(секунда), измерение `Номенклатура`, ресурс `Цена` (15,2).

### 6.1. Чтение старых цен

Один запрос на все товары:

```
ВЫБРАТЬ
    Цены.Номенклатура КАК Номенклатура,
    Цены.Цена КАК Цена
ИЗ
    РегистрСведений._ДемоЦеныНоменклатуры.СрезПоследних(
        &Граница, Номенклатура В (&Номенклатура)) КАК Цены
```

- `&Граница = ДобавитьКДате(НачалоДня(ДатаПереоценки), "Секунда", -1)`;
- отбор — в параметре виртуальной таблицы, не в `ГДЕ`;
- `Номенклатура` — ключевое поле измерения, индекс есть по ключу;
- товар без строки в результате — `no_price`.

### 6.2. Запись

Для каждого переоценённого товара:

```
Менеджер = РегистрыСведений._ДемоЦеныНоменклатуры.СоздатьМенеджерЗаписи();
Менеджер.Период = НачалоДня(ДатаПереоценки);
Менеджер.Номенклатура = Товар;
Менеджер.Цена = НоваяЦена;
Менеджер.Записать();
```

Запись выполняется в одной транзакции; при ошибке — откат и проброс исключения.
Явные блокировки не ставятся: запрос идемпотентен по ключу «период + товар»,
сценарий — одиночный запрос магазина. Если потребуется защита от гонки, она
добавляется отдельно и не входит в приёмку.

### 6.3. Идемпотентность

Повторный запрос с той же датой:

- старые цены читаются на конец предыдущего дня, поэтому новая запись
  этой же даты в срез не попадает;
- запись с тем же периодом и товаром заменяет прежнюю;
- результат — те же числа.

## 7. Компоненты и поток

```
POST /prices/reprice
  -> HTTPServices/СчетаМагазина/Ext/Module.bsl: ПереоценитьТовары(Запрос)
  -> СчетаМагазинаHTTP.ПереоценитьТовары(Запрос)
       - Content-Type, JSON, поля, ошибки invalid_data
       - СчетаМагазинаДанные.ПереоценитьТовары(Товары, Процент, Дата)
            - СрезПоследних -> oldPrice / no_price
            - РассчитатьНовуюЦену
            - транзакция: МенеджерЗаписи.Записать()
       - ОтветJSON(200, repriced/skipped)
```

Тесты интеграции вызывают `СчетаМагазинаHTTP.ПереоценитьТовары` с заглушкой
`ЮТест.Данные().HTTPСервисЗапрос()`; публикация не нужна.

## 8. Тесты

### 8.1. Юнит (тег `unit`, модуль `СчетаМагазинаТесты_Юнит`)

| Правило | Тест | Значения | Ожидание |
| --- | --- | --- | --- |
| Процент вверх | `НоваяЦена_ПроцентВверх` | 100, +7 | 107 |
| Процент вниз с округлением | `НоваяЦена_ПроцентВнизОкругление` | 151, −30 | 106 |
| Половина рубля вверх | `НоваяЦена_ПоловинаРубляВверх` | 150, +7 | 161 |

### 8.2. Интеграционные (тег `integration`, модуль `СчетаМагазинаТесты_Интеграционные`)

| Правило | Тест | Проверка |
| --- | --- | --- |
| Новая цена с начала дня, старая в истории | `Переоценка_НоваяЦенаСНачалаДня` | 3 товара, +7, завтра; ответ и срез на дату/предыдущий день |
| Товар без цены пропущен | `Переоценка_ТоварБезЦеныПропущен` | дата в прошлом; один товар с ценой, один без; `skipped` = `no_price` |
| Повторная дата не меняет цену | `Переоценка_ПовторнаяДатаНеМеняетЦену` | два вызова +7; обе цены 107, записей на дату одна |
| Неверный процент | `Переоценка_НеверныйПроцентНеПишет` | 150 -> 400 `invalid_data`, путь `percent`, в регистре на дату пусто |

### 8.3. Охранные проверки входа (без Red)

Ожидаемо зелёные с первого прогона после реализации валидации; в плане помечены
как охранные:

- пустой `items`;
- повтор товара -> `items[1]`;
- несуществующий товар -> `items[0]`;
- помеченный на удаление товар -> `items[0]`;
- неверная дата -> `date`;
- `percent = 0` -> `percent`;
- границы `-50` и `100` -> `200`;
- `percent` строкой -> `percent`;
- `items` не массив -> `items`;
- `date` не строка -> `date`.

### 8.4. Данные тестов

- даты считаются от `ТекущаяДатаСеанса()`: «завтра» для обычных переоценок,
  «вчера» для товара без цены;
- начальная цена пишется на `23:59:59` предыдущего дня;
- автоматическая цена, которую пишет демо-конфигурация при создании товара,
  не мешает: для «завтра» начальная цена позже неё, для «вчера» она позже даты
  переоценки;
- очистка: удалить все записи регистра по товару (набор с отбором
  `Номенклатура`, `Прочитать`/`Очистить`/`Записать`), затем удалить товар;
- очистка вызывается и после красного (`Попытка / Исключение`).

### 8.5. Конфиги

- `tests/unit.json`, `tests/integration.json` — существующие;
- добавить `tests/all.json` без `tags` — общий прогон;
- ожидаемое число тестов: 15 юнит (12 старых + 3 новых), 18 интеграционных
  (4 старых + 4 новых + 10 охранных), всего 33.

## 10. Риски и допущения

1. Маршрут HTTP-сервиса — изменение состава метаданных расширения. В
   `HTTPServices/СчетаМагазина.xml` добавляются `URLTemplate` и `Method`
   с новыми UUID, в `ConfigDumpInfo.xml` — соответствующие дочерние записи.
   После загрузки проверяется дамп расширения и наличие `/prices/reprice`;
   при проблеме загрузки маршрут добавляется через Конфигуратор.
2. Токен процента извлекается из тела запроса; при нестандартном JSON
   (пробелы, экспонента) токен всё равно читается до разделителя.
3. Автоматическая цена при создании товара учтена выбором дат; тесты
   не полагаются на её отсутствие.
4. Безопасный режим расширений после загрузки снимается `ibcmd`; на время
   `ibcmd` публикация Apache останавливается (требование монопольного доступа).
5. Тесты используют относительные даты, поэтому не зависят от календаря.
6. Модуль `СчетаМагазинаДанные` исторически без лицензионного заголовка и областей
   (известный долг из `AGENTS.md`). В этом изменении новые экспортные функции
   снабжаются doc-комментариями; полная нормализация модуля — отдельная задача,
   чтобы не раздувать diff этой доработки.
